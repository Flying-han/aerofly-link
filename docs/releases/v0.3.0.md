# Aerofly Link 0.3.0

## Highlights

- Native C11/Win32 client is the only shipped implementation; Windows CLI and GUI are built with the vfox-managed `zig cc` toolchain.
- New settings default to VATSIM FSD-JWT authentication (revision 100). `jwt_url`, FSD host/port, server lists, and the JWT-only proxy remain user-configurable; legacy revision 9 remains an explicit compatibility mode.
- JWT token requests can use Windows automatic proxy settings or a per-application WinHTTP proxy list (`jwt_proxy` / `jwt_proxy_bypass`), so community deployments can use their own network route without changing global proxy settings.
- FSD session interoperability fixes: remove the invalid two-field `#SB` login packet, send cached-position keepalives instead of `#TM...:SERVER:@`, and preserve the current STBY/IDENT/transponder code in keepalive packets.
- Fix a VATSIM login use-after-scope bug that truncated the JWT before `#AP` construction. Debug traces redact both legacy passwords and JWTs.
- Preserve callsign/CID, authentication type, and flight-plan settings in the GUI. Fix the 46-entry workspace visibility list overrunning its 40-handle storage, which corrupted connection-page handles; do not clear the initial saved flight plan. Rebuild `libfsd.a` cleanly so stale test/UI objects cannot enter the release executable.
- Remove the superseded Python client, Python test suite, old Python installer, and unused in-repository C++ DLL scaffold. Keep Python only for the two development GUI/Mock utilities.

## Verification

- vfox Zig 0.15.1 `client-c\build.cmd`: 170 protocol checks and 106 session/bridge/config checks passed.
- Local ASC FSD 0.6.2 source image (`8142a8570c1f3ca612734363cdefe637fc0d2c97`): VATSIM revision-100, two-client long-session, position/flight-plan/chat, STBY keepalive, invalid JWT rejection, Redis fail-closed/recovery, GUI login, and disconnect cleanup passed. Detailed scope and limits: [local FSD E2E report](../testing/e2e-fsd-client.md).
- The local E2E uses a test-only link-time JWT provider for the C VATSIM session path. It does not verify the production WinHTTP HTTPS token-acquisition success path or public/production connectivity.
