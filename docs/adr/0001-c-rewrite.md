# ADR 0001: 客户端以 C 语言重写（协议层先行）

- 状态: 已接受（2026-09-18）
- 关联: [C 重写架构与开发计划](../C_REWRITE_PLAN.md)、ADR 0005（性能预算）

## 背景

用户反馈与社区现状：

1. 安装体积大（PyInstaller 打包 ~127MB），运行内存占用高（PyQt6 + Python 运行时基线），
   且在游戏未运行时仍存在后台空转（1.1.0 已修复空转部分，但体积/内存地板由技术栈决定）。
2. ASC 社区已有以 C 重写客户端的计划。
3. 工具链具备：本机 vfox 管理的 zig cc 可作为 C 编译器（单命令交叉编译，无 MSVC 依赖）。

## 事实基础（第一性拆解）

Python/PyQt 方案的成本地板：

| 项目 | 来源 | 量级 |
| --- | --- | --- |
| 安装体积 | Python 运行时 + Qt6 DLL 集合 | ~127MB（bc33b6d 移除地图后） |
| 常驻内存 | CPython 解释器 + Qt Widgets + asyncio | ~100-200MB |
| 启动时延 | 解释器初始化 + Qt 加载 | 秒级 |
| 分发形态 | PyInstaller 文件夹 + 安装器 | 需打包整个运行时 |

C 原生方案的理论值：二进制 1-3MB、常驻内存个位数至十几 MB、启动毫秒级。
FSD 客户端的核心逻辑（TCP 行协议解析/构造、位打包、定时器）恰好是 C 的舒适区，
不依赖任何重型库；唯一重型面（UI）可以后置。

## 考虑过的替代方案

| 方案 | 结论 |
| --- | --- |
| 继续优化 Python | 已做（1.1.0：空转、内存上限、依赖清理），但体积/内存地板不变，ROI 递减 |
| Rust | 内存安全优，但与社区 C 重写方向不一致，学习/构建成本高 |
| C++ | 仅 DLL 脚手架在用；新客户端无需其抽象能力，ABI 与构建复杂度是净负担 |
| Go（与后端同栈） | 二进制 ~10MB+、GC、单文件分发可以，但 GUI 生态弱，且与社区决定不一致 |

## 决策

1. 以 **C11** 重写客户端，目录 `client-c/`，与 Python 实现共存过渡。
2. **协议层先行**：先移植并固化 FSD 协议层（与 `core/fsd_protocol.py`、
   `core/fsd_client.py` 的报文构造/解析逻辑逐条对齐，用同一组测试用例校验），
   再向上搭 DLL 桥接与传输层，UI 最后。
3. 编译器使用 **zig cc**（vfox 管理），构建脚本用显式命令（`client-c/build.cmd`），
   代码保持 MSVC 兼容的 C11（不用 GNU 扩展），保留换用 MSVC/Clang 的退路。
4. Python 版在过渡期保持可用并作为**行为参照**；两者对接同一个 Mock 契约
   （`core/mock_server.py`）与同一个 ASC FSD 0.5.3 服务端做互操作验证。
5. 参考实现：[swift-project](https://github.com/swift-project/swift) 的 FSD 协议层
   （PBH 位布局、坐标格式、dialect 处理）——仅借鉴协议行为，不复制代码（许可证差异）。

## 后果

- 过渡期存在两套实现，文档必须标注"哪边是事实标准"（当前：Python 行为为基准，
  C 逐条对齐后以 C 为准，见计划的 P2 验收）。
- C 层无 GC / 无异常，错误处理采用返回码约定（见计划第 5 节），新贡献者需先读
  `client-c/README.md`。
- UI 阶段（P3）技术选型（Win32 / Qt C++ / web 前端壳）本 ADR 不锁定，
  到达 P3 时另立 ADR。
